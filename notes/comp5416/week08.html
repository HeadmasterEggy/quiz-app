题型 1　客户端缓冲与下溢 ★★★

三类多媒体应用：流式存储（YouTube，边下边播，可以比播放更快地传）、会话式（Skype，时延容忍度最低）、直播。

服务器按固定节奏发，但网络时延有抖动（jitter）；视频一旦开播必须按原节奏连续播。办法：客户端缓冲 + 播放时延，先攒一段再播。

  • 播放时延太小 → 某块到播放时刻还没到 → 缓冲下溢（卡顿）。
  • 加大播放时延 → 下溢更少，代价是用户等更久才开始看。

$x(t)$ 填充速率（会变），$r$ 播放速率（恒定），$Q(t)$ 缓冲量，$t_p$ 开播时刻：

$$Q(t+1) = \begin{cases} Q(t) + x(t), & t \le t_p\ \ \text{（只进不出）}\\ \max[\,Q(t) + x(t) - r,\ 0\,], & t > t_p \end{cases}$$

$Q(t) + x(t) - r < 0$ 就是下溢。

必考结论
  • E(x) < r：缓冲迟早被抽空，视频卡住。
  • E(x) ≥ r：缓冲不会空，前提是初始播放时延足够大，能吸收 x(t) 的波动。

例题

r = 2，Q(0) = 0，x(0..5) = 2, 2, 1, 0, 3, 2。

r = 2，Q(0) = 0，x(0..3) = 2, 2, 1, 0，$t_p = 0$。哪个时刻第一次出现下溢（$Q(t) + x(t) - r < 0$）？
  1. t = 1

Q(1) = 2，Q(2) = 2 + 2 − 2 = 2，Q(3) = 2 + 1 − 2 = 1；t = 3 时 1 + 0 − 2 < 0。

DASH（Dynamic Adaptive Streaming over HTTP）

  • 服务器：视频切成块，每块用多种码率编码；manifest 文件列出各版本 URL。
  • 客户端：定期测带宽，查 manifest，一次请求一块，选当前带宽撑得住的最高码率；不同时间可以选不同码率。
  • 客户端决定三件事：何时请求下一块（不让缓冲饿死或溢出）、请求什么码率、从哪里请求。
关于 DASH，正确的是？
  1. 服务器把视频切块，多码率编码
  2. manifest 给出各个版本的 URL
  3. 由服务器决定发哪个码率
  4. 客户端可在不同时间选不同码率
DASH 的智能在客户端。

题型 3　CDN 与 DNS 重定向 ★★

一个超大服务器不可扩展：单点故障、网络拥塞点、到远处用户路径长、同一视频多个副本挤在出口链路。CDN：在地理上分布的很多站点放副本，就近服务。

DNS 重定向（讲义：Bob 看 netcinema 的视频，内容在 KingCDN）

  1. 视频预先存进 KingCDN；Bob 从网页拿到 URL netcinema.com/6Y7B23V。
  2. Bob 的本地 DNS 解析这个名字。
  3. netcinema 的权威 DNS 不返回 IP，而是返回一个 KingCDN 的名字（W04 的 CNAME 思路）。
  4. 本地 DNS 再问 KingCDN 的权威 DNS，它返回「最好」的 KingCDN 服务器的 IP。
  5. Bob 向那台服务器请求，HTTP 流式传输。
选节点策略做法
地理最近最简单
时延最短 / 跳数最少CDN 节点定期 ping 各接入 ISP，结果报给 CDN 的 DNS
让客户端自己选给客户一份服务器列表，客户 ping 后挑最好的：讲义里 Netflix 的做法

Netflix（讲义 2011 年架构）：自己只管注册和计费服务器；Amazon 云生成多种编码、上传到 CDN、托管网页；内容放在三家 CDN（Akamai、Limelight、Level-3）。流程：账户 → 选片 → 返回 manifest → DASH 播放。

CDN 一般怎么把用户引到合适的服务器？
  1. 修改 IP 层的路由表
  2. 权威 DNS 返回 CDN 名字，CDN 的 DNS 返回节点 IP
  3. 用 HTTP 301 永久重定向
  4. 客户端在局域网内广播查询
内容提供商把解析权交给 CDN，CDN 的 DNS 按请求来源挑节点。

题型 4　码率计算 ★★

音频三步：采样（电话 8000 次/秒，音乐 44100 次/秒）→ 量化（四舍五入到如 256 个值，差值是量化误差）→ 编码（256 个值要 8 bit）。

$$\text{码率} = \text{采样率}\times\text{每样本比特数}\qquad \text{电话 } 8000\times8 = 64\text{ kbps};\ \ \text{音乐 } 44100\times8 = 352.8\text{ kbps}$$

视频：$8\times3\times480\times640\times24 \approx 177$ Mbps，必须压缩：

  • 空间编码（帧内）：一行 N 个同色像素只发「颜色 + 重复次数」。
  • 时间编码（帧间）：只发和前一帧的差别。
  • MPEG-1（CD-ROM）1.5 Mbps；MPEG-2（DVD）3–6 Mbps；MPEG-4（互联网）< 1 Mbps。分 CBR 和 VBR。
关于视频压缩，正确的是？
  1. 空间编码只发颜色和重复次数
  2. 时间编码只发和前一帧的差别
  3. MPEG-2 用于 DVD，约 3–6 Mbps
  4. MPEG-4 码率一般高于 MPEG-1
MPEG-4 < 1 Mbps，MPEG-1 是 1.5 Mbps。

题型 5　VoIP 与播放时延 ★★

  • 端到端时延：< 150 ms 好，> 400 ms 差。
  • 讲话段与静默期交替；讲话时 64 kbps，每 20 ms 一块 = 160 字节，只在讲话时产生数据。
  • 两种丢失：网络丢失（路由器缓冲溢出）和时延丢失（到得太晚赶不上播放，等于丢了）。丢包容忍 1%–10%，看编码和丢包隐藏。

固定播放时延 q

时间戳 t 的块在 t + q 播放，之后才到的算丢失。q 大：丢得少、交互差；q 小：交互好、丢得多。

自适应播放时延

估计网络时延，在每个讲话段开始时调整，静默期被压缩或拉长：

$$d_i = (1-u)\,d_{i-1} + u\,(r_i - t_i)\qquad v_i = (1-u)\,v_{i-1} + u\,|r_i - t_i - d_i|$$ $$\text{讲话段第一个分组播放时刻} = t_i + d_i + K v_i$$

$r_i$ 接收时刻，$t_i$ 时间戳，$u$ 如 0.01。$d_i$、$v_i$ 每个分组都更新，但只在讲话段开头用。和 TCP 的 EstRTT + 4 DevRTT 同一个思路。

例：$u = 0.01$，$d_{i-1} = 100$，$v_{i-1} = 10$，实测 150（ms）→ $d_i = 100.5$，$v_i = 9.9 + 0.495 = 10.395$；K = 4 时播放时刻 $= t_i + 142.08$ ms。

判断新讲话段
  • 不会丢包：相邻时间戳差 > 20 ms → 新讲话段。
  • 可能丢包：时间戳差 > 20 ms 且序号连续 → 新讲话段；序号跳了说明是丢包。

例：序号 1、3、4、5，时间戳 0、40、100、120。0 → 40 差 40 但序号跳了（丢了 2）；40 → 100 差 60 且序号连续 → 100 是新讲话段第一个。

可能丢包时，怎么判断一个分组是新讲话段的第一个？
  1. 与上一个时间戳差大于 20 ms
  2. 与上一个分组的序号不连续
  3. 时间戳差大于 20 ms 且序号连续
  4. 时间戳差等于 20 ms 且序号跳了
只看时间戳会把「丢了一个包」当成「静默」。

题型 6　丢包恢复 ★★

可容忍时延很小，ACK/NAK 来回一个 RTT 来不及重传，所以用前向纠错（FEC）等办法。

方案做法带宽开销额外时延效果
XOR FEC每 n 块加 $y = x_1\oplus\cdots\oplus x_n$$1/n$等一组 n + 1 个完全恢复，一组最多丢 1 个
低质量冗余流第 n 个分组捎带第 n − 1 块的低质版本（如 64 kbps 主流 + 13 kbps 冗余）冗余流码率一个分组降质恢复
交织每块切成小单元（如 4 个 5 ms），每个分组装来自不同块的单元0较大隐藏：每块只缺一小片

XOR 例（n = 3）：$x_1 = 1$，$x_2 = 0$，$x_3$ 丢，$y = 0$ → $1\oplus0\oplus x_3 = 0$ → $x_3 = 1$。n 越大开销越小，但恢复要等更久。交织：不交织丢一个分组 = 丢一整个单词；交织 = 每个单词缺一个音节。

关于丢包恢复，正确的是？
  1. XOR FEC 每 n 块加 1 块，开销 1/n
  2. XOR FEC 一组丢 2 块也能恢复
  3. 交织无冗余开销但时延更大
  4. 低质量冗余流丢包后降质顶上
XOR 一组最多丢 1 块。

题型 7　RTP ★★

  • 规定承载音视频的分组格式（RFC 3550）：载荷类型、序号、时间戳。跑在端系统上，封装在 UDP 段里。
  • RTP 不提供 QoS：没有保证及时交付的机制；中间路由器看不到 RTP 首部，照样尽力而为。
字段位数作用
payload type7编码类型；中途换编码靠它告诉接收方（0 = PCM μ-law 64 kbps，3 = GSM 13 kbps）
sequence number16每个分组 +1；发现丢包、恢复顺序
timestamp32分组第一个字节的采样时刻
SSRC32标识流的来源，同一会话里每个流不同
时间戳增量

音频每个采样周期时间戳 +1。8 kHz → 每 125 μs +1；每块 20 ms = 160 个样本 → 每个分组 +160。静默时时钟照样走。

时间戳 X、X + 160、X + 480：中间跳过 2 块。时间戳跳 + 序号也跳 → 丢包；时间戳跳 + 序号连续 → 新讲话段。

8 kHz 采样、每块 20 ms 的音频，相邻 RTP 分组的时间戳相差多少？
  1. 1
  2. 20
  3. 160
  4. 8000
20 ms / 125 μs = 160 个样本。

考前速记

  1. 缓冲：时延太小下溢；E(x) < r 必卡；E(x) ≥ r 还要够大的初始时延；会用递推。
  2. UDP 流恒速、2–5 s、可能被防火墙挡；HTTP 流 TCP 最大速率、时延长；DASH 切块多码率 + manifest，客户端选。
  3. CDN：权威 DNS 返回 CDN 名字，CDN DNS 返回节点 IP；Netflix 让客户端选。
  4. 码率 = 采样率 × 比特；电话 64 kbps；未压缩视频约 177 Mbps；MPEG-1/2/4 = 1.5 / 3–6 / <1 Mbps。
  5. VoIP < 150 ms 好、> 400 ms 差；20 ms 一块 160 B；网络丢失 + 时延丢失。
  6. 自适应：$t_i + d_i + Kv_i$，只在段首调整；新讲话段 = 时间戳差 > 20 ms 且序号连续。
  7. XOR FEC 开销 1/n、一组最多丢 1；低质冗余降质；交织零开销、时延大。
  8. RTP 在 UDP 里、不提供 QoS；PT 7 位、序号 16 位、时间戳 32 位、SSRC 32 位；每包 +160。
